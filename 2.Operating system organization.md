### 2.5 Process overview

进程就是隔离的最小单元.

OS为进程提供幻象,私有内存空间,独占CPU:

​	To help enforce isolation, the process abstraction provides the illusion to a program that it has its own private machine. A process provides a program with what appears to be a private memory system, or address space, which other processes cannot read or write. A process also provides the program with what appears to be its own CPU to execute the program’s instructions.

硬件采用页表来实现:

​	Xv6 uses page tables (which are implemented by hardware) to give each process its own address space. The RISC-V page table translates (or “maps”) a virtual address (the address that an RISC-V instruction manipulates) to a physical address (an address that the CPU chip sends to main memory).

为每个进程维护了一个页表,进程认为自己使用一个地址从零开始的地址空间:

![image-20250917155316890](../../../mio/static/img/image-20250917155316890.png)

​	Instructions come first, followed by global variables, then the stack, and finally a “heap” area (for malloc) that the process can expand as needed. There are a number of factors that limit the maximum size of a process’s address space: pointers on the RISC-V are 64 bits wide; the hardware only uses the low 39 bits when looking up virtual addresses in page tables; and xv6 only uses 38 of those 39 bits. Thus, the maximum address is 238 − 1 = 0x3fffffffff, which is MAXVA (kernel/riscv.h:348). 

用户栈和内核栈(分离的):

Each process has a thread of execution (or thread for short) that executes the process’s instructions. A thread can be suspended and later resumed. To switch transparently between processes, the kernel suspends the currently running thread and resumes another process’s thread. Much of the state of a thread (local variables, function call return addresses) is stored on the thread’s stacks. Each process has two stacks: **a user stack and a kernel stack (p->kstack)**. When the process is executing user instructions, only its user stack is in use, and its kernel stack is empty. When the process enters the kernel (for a system call or interrupt), the kernel code executes on the process’s kernel stack; while a process is in the kernel, its user stack still contains saved data, but isn’t actively used. A process’s thread alternates between actively using its user stack and its kernel stack. The kernel stack is separate (and protected from user code) so that the kernel can execute even if a process has **wrecked** its user stack.

进程的状态,I/O阻塞:

​	p->state indicates whether the process is **allocated, ready to run, running, waiting for I/O, or**
**exiting**.
​	p->pagetable holds the process’s page table, in the format that the RISC-V hardware expects. xv6 causes the paging hardware to use a process’s p->pagetable when executing that process in user space. A process’s page table also serves as the record of the addresses of the physical pages allocated to store the process’s memory.

### 2.6 Code: starting xv6 and the first process

第一个进程运行的过程:

​	电源打开,初始化,运行ROM里面的bootloader,bootloader把kernel的代码加载进入主存,执行_entry中的代码,这个时候虚拟内存和物理内存是一样的,没有转换(取消硬件的页表转换).

​	When the RISC-V computer powers on, it initializes itself and runs a boot loader which is stored in read-only memory. The boot loader loads the xv6 kernel into memory. Then, in machine mode, the CPU executes xv6 starting at _entry (kernel/entry.S:6). The RISC-V starts with paging hardware disabled: virtual addresses map directly to physical addresses.

加载到物理内存的一个位置:

​	The loader loads the xv6 kernel into memory at physical address 0x80000000. The reason it places the kernel at 0x80000000 rather than 0x0 is because the address range 0x0:0x80000000 contains I/O devices.

创建堆栈,能运行C代码:

​	The instructions at _entry set up a stack so that xv6 can run C code. Xv6 declares space for an initial stack, stack0, in the file start.c (kernel/start.c:11). The code at _entry loads the stack pointer register sp with the address stack0+4096, the top of the stack, because the stack on RISC-V grows down. Now that the kernel has a stack, _entry calls into C code at start (kernel/start.c:21).

​	The function start performs some configuration that is only allowed in machine mode, and
then **switches to supervisor mode**. To enter supervisor mode, RISC-V provides the instruction **mret**. This instruction is most often used to **return from a previous call from supervisor mode to machine mode**. start isn’t returning from such a call, and instead sets things up as if there had been one: it sets the previous privilege mode to supervisor in the register **mstatus**, it sets the return address to **main** by writing main’s address into the register mepc, disables virtual address translation in supervisor mode by writing 0 into the page-table register **satp**, and delegates all interrupts and exceptions to supervisor mode.
​	Before jumping into supervisor mode, start performs one more task: **it programs the clock chip to generate timer interrupts**. With this housekeeping out of the way, start “returns” to supervisor mode by calling mret. This causes the program counter to change to main (kernel/main.c:11). After main (kernel/main.c:11) initializes several devices and subsystems, it creates the first process by calling **userinit** (kernel/proc.c:212). The first process executes a small program written in RISC-V assembly, initcode.S (user/initcode.S:1), which re-enters the kernel by invoking the exec system call. As we saw in Chapter 1, exec replaces the memory and registers of the current.

`_entry` 处的指令建立了一个栈，以便 xv6 能运行 C 代码。xv6 在文件 `start.c`（`kernel/start.c:11`）中为初始栈声明了空间 `stack0`。`_entry` 处的代码把栈指针寄存器 `sp` 载入地址 `stack0+4096`（即栈顶），因为在 RISC-V 上栈向下增长。现在内核已有栈，`_entry` 调用 C 代码 `start`（`kernel/start.c:21`）。

函数 `start` 执行了一些只能在机器模式（machine mode）下完成的配置，然后**切换到监督者模式（supervisor mode）**。为了进入监督者模式，RISC-V 提供了指令 `mret`。该指令最常用于在从监督者模式进入机器模式之后将控制返回（即从机器模式返回到先前的监督者模式）。`start` 并不是从这样的调用中返回；它改为把系统设置成好像发生过这样的返回：它在寄存器 `mstatus` 中将先前的特权模式设置为监督者（supervisor），通过把 `main` 的地址写入寄存器 `mepc` 将返回地址设置为 `main`，通过把 `0` 写入页表寄存器 `satp` 来禁用监督者模式下的虚拟地址转换，并把所有中断和异常委派给监督者模式。

在跳入监督者模式之前，`start` 还要做一件事：它对时钟芯片进行编程，使其产生定时器中断。完成这些收尾工作后，`start` 通过执行 `mret` “返回”到监督者模式。这样会使程序计数器（PC）跳转到 `main`（`kernel/main.c:11`）。`main`（`kernel/main.c:11`）初始化若干设备和子系统后，通过调用 `userinit`（`kernel/proc.c:212`）**创建第一个进程**。第一个进程执行一段用 RISC-V 汇编编写的小程序 `initcode.S`（`user/initcode.S:1`），该程序通过调用 `exec` 系统调用重新进入内核。正如我们在第 1 章看到的，`exec` 会替换当前进程的内存和寄存器。

应该是不支持**一个进程拥有多线程**.

### lab2

1.理解整个syscall的流程:

------

1. 用户态调用库函数

用户程序不会直接写 `ecall`，而是调用封装好的库函数。例如：

```c
// 用户态
#include "kernel/syscall.h"

int pid = getpid();
```

这里的 `getpid()` 并不是直接取进程号，而是调用用户态的封装函数。
 在 xv6 的 `user/usys.pl` 脚本会生成一些用户态的系统调用桩代码，比如：

```asm
.global getpid
getpid:
    li a7, SYS_getpid  // 把系统调用号放到寄存器 a7
    ecall              // 触发 RISC-V 的陷入（进入内核态）
    ret
```

------

2. 进入内核态（Trap / Exception）

执行 `ecall` 指令后，CPU 切换到内核态：

- 当前的用户态 PC 和寄存器会保存到内核栈（trapframe）。
- CPU 跳转到内核中设置好的 **trap handler**，即 `kernel/trap.c` 里的 `usertrap()`。

------

3. Trap Handler 调用 syscall()

在 `usertrap()` 里，内核会发现这是一个系统调用（`ecall`），于是调用：

```c
syscall();
```

------

4. syscall() 函数

在 `kernel/syscall.c` 里：

```c
void syscall(void) {
  int num;
  struct proc *p = myproc();

  num = p->trapframe->a7;   // 从 trapframe 中取出系统调用号
  if(num > 0 && num < NELEM(syscalls) && syscalls[num]) {
    p->trapframe->a0 = syscalls[num]();  // 调用对应的 sys_* 函数
  } else {
    printf("%d %s: unknown sys call %d\n",
            p->pid, p->name, num);
    p->trapframe->a0 = -1;
  }
}
```

这里的关键点：

- `a7` 保存了系统调用号（用户态桩代码里写入的）。
- `syscalls[]` 是一个函数指针表，把系统调用号映射到 `sys_*` 函数。
- `a0` 作为返回值（寄存器传递），最终会返回到用户态。

比如 `SYS_getpid` 对应 `sys_getpid()`，就会执行。

------

5. sys_* 函数

`sys_*` 函数是内核里的具体实现，例如 `kernel/sysproc.c` 里：

```c
uint64
sys_getpid(void) {
  return myproc()->pid;
}
```

这个函数就是真正的内核逻辑，直接访问 `proc` 结构体，返回进程号。

------

6. 返回**用户态**

当 `sys_*` 函数执行完：

- 返回值放在 `p->trapframe->a0`。
- `usertrapret()` 会恢复用户寄存器状态，把 `a0` 返回到用户态。
- 用户程序继续运行，好像只是普通函数调用了一样。

------

总结流程（以 getpid 为例）：

1. **用户态**：调用 `getpid()` → 把系统调用号放进 `a7` → `ecall`。
2. **进入内核**：陷入 `usertrap()`。
3. **内核调度**：调用 `syscall()`，查表找到 `sys_getpid()`。
4. **执行内核逻辑**：`sys_getpid()` 返回当前进程 pid。
5. **返回用户态**：返回值写到 `a0` → 回到用户程序。
